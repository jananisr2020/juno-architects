# Support and professional review workflow

## Before requesting help
1. Record the application version and current incident ID if the error screen provides one.
2. Download the optional privacy-safe diagnostic JSON. It contains no stack trace or project details.
3. Describe the page and the steps that caused the issue. Do not attach passwords, bearer tokens, street-level property details, or private project payloads.
4. Include the browser/device only if it is relevant to reproducing the issue.

## Professional review requests
A signed-in user can submit a review request from a saved cloud project. The API records the request and its status. The current implementation does not automatically assign an architect, send an email, quote a fee, or guarantee a response. A real professional network, identity/licence checks, service-level expectations, payment terms and notification delivery must be established before offering this as a paid service.

## What a concept review does not mean
A review request or status is not a permit, planning approval, structural certification, construction drawing, or guarantee of code compliance. The user must engage a suitably licensed local architect/engineer and the competent authority for final drawings and approvals.

## Production incident handling
Before public launch, assign an owner for support requests, define response targets, add a private ticketing channel, document severity levels, configure provider-level uptime alerts, and rehearse rollback and database restoration. Do not route project payloads or authentication secrets into public GitHub issues.
